> **สำหรับ Claude:** ไฟล์ `ia-lab.html` ที่แนบมาคือต้นฉบับที่ทำงานได้แล้ว ให้ใช้เป็น source of truth
> งานของคุณคือสร้างเว็บนี้ขึ้นใหม่ใน account นี้เป็น **Claude Artifact** ที่ทีมใช้ได้จริง โดยคงพฤติกรรม เนื้อหา และหน้าตาเดิมไว้ทั้งหมด
> ถ้า requirement ในเอกสารนี้ขัดกับโค้ดใน HTML ให้ยึดตามเอกสารนี้ แล้วแจ้งเจ้าของว่าต่างกันตรงไหน

## 1. เป้าหมาย

เจ้าของกำลังทำ **design system portal** และต้องตัดสินใจว่าจะวาง IA ของ component ยังไงให้ดีไซเนอร์หาของง่าย
เว็บนี้ให้ทีม UI ทุกคนมาทำแบบทดสอบ 2 แบบ แล้วเจ้าของดูผลรวมเพื่อตัดสินใจโครงเมนู

- **Card sort:** ให้คนจัด component เป็นกลุ่มและตั้งชื่อกลุ่มเอง ได้ไอเดียการจัดกลุ่มและชื่อที่ทีมใช้
- **Tree test:** ให้คนลองหาของในเมนูที่ร่างไว้ ได้คำตัดสินว่าโครงไหนหาของเจอง่ายกว่า และต้องแก้ตรงไหน

ผู้ใช้มี 2 กลุ่ม:
1. **ผู้ตอบ** (ทีม UI) ได้ลิงก์ไปทำแบบทดสอบ
2. **เจ้าของ** ดูผลลัพธ์โดยใส่รหัส `0000`

## 2. ข้อกำหนดหลัก

- **ภาษา:** UI เป็นภาษาไทยทั้งหมด ชื่อ component เป็นภาษาอังกฤษ
- **รูปแบบ:** Claude Artifact ไฟล์ HTML เดียว (vanilla JS ไม่ใช้ framework) ใช้ฟอนต์ IBM Plex Sans Thai และ IBM Plex Mono จาก Google Fonts
- **ธีม:** รองรับ light/dark ตาม token ใน `:root` ของต้นฉบับ
- **มือถือ:** ใช้ได้ที่ความกว้างประมาณ 400px (card sort ใช้การ "กดเลือกการ์ด → กดกลุ่ม" แทนการลากบนมือถือได้)
- **ความเป็นส่วนตัว:** ผู้ตอบห้ามเห็นคำตอบของคนอื่น

## 3. Runtime capabilities และสิทธิ์ข้อมูล (สำคัญ)

ประกาศ capabilities ตอน publish ตามนี้:

```json
{
  "db": { "rules": [
    { "path": "responses",        "read": "admin",    "write": "admin" },
    { "path": "responses/{self}", "read": "interact", "write": "interact" }
  ]},
  "user": { "scopes": ["profile"] },
  "downloads": true
}
```

- ผู้ตอบ 1 คน = เอกสาร 1 ชิ้นที่ `responses/<userId>` (ได้ id จาก `await (await claude.use("user")).me()`)
- ผู้ตอบเขียนและอ่านได้เฉพาะเอกสารของตัวเอง ส่วนเจ้าของ (owner/admin) อ่านได้ทั้ง collection
- **รหัส `0000` เป็นแค่ประตูหน้าจอ** ไม่ได้ป้องกันข้อมูล ที่ป้องกันจริงคือ rules ด้านบน ต่อให้คนอื่นใส่รหัสถูกก็เห็นผลว่าง
- เข้าถึง capability ผ่าน `claude.use(...)` เท่านั้น และรองรับกรณีได้ค่า `null` (ขึ้นข้อความว่า "บันทึกคำตอบไม่ได้")
- ตรวจหลัง publish:
  1. ใช้ ArtifactData ใส่เอกสารทดสอบในฐานะเจ้าของ
  2. `list` ด้วย `as_level: "interact"` ต้องไม่เห็นเอกสารนั้น
  3. ลบเอกสารทดสอบทิ้ง
- **เจ้าของต้องแชร์ลิงก์ให้ทีมเป็นสิทธิ์ "Can interact"** ถ้าแชร์แค่ "Can view" ทีมจะส่งคำตอบไม่ได้ แจ้งเจ้าของตอนส่งลิงก์

### โครงสร้างเอกสารผู้ตอบ

```js
  }

```

## 4. หน้าและพฤติกรรม

แท็บบนสุด: **หน้าแรก · 1 · Card sort · 2 · Tree test · ผลลัพธ์** (แท็บที่ทำแล้วมีจุดสีเขียว)

### 4.1 หน้าแรก
- ช่อง **"ชื่อของคุณ"** ใส่ชื่อจากบัญชีไว้ให้ก่อนแล้วแก้ได้ ต้องกรอกก่อนปุ่มเริ่มจะกดได้ และบันทึกเป็น `displayName`
- การ์ดอธิบายวิธีทำ 2 ใบ (Card sort ~10–15 นาที · Tree test ~5 นาที) พร้อมปุ่มเริ่ม และสถานะ "ทำแล้ว ✓"

### 4.2 Card sort (open sort)
- การ์ด **52 ใบ** (รายการอยู่ในข้อ 5.1) แต่ละใบมีเลข ชื่อ และคำอธิบายภาษาไทยสั้น ๆ สลับลำดับแบบสุ่ม
- สร้างกลุ่มได้ไม่จำกัด ตั้งชื่อกลุ่มเอง ลบกลุ่มได้ (การ์ดในกลุ่มกลับไปกองกลาง)
- มีกอง **"ไม่แน่ใจ"**
- ย้ายการ์ดได้ 2 วิธี: กดการ์ดแล้วกดกลุ่มปลายทาง หรือลากวาง (HTML5 DnD)
- บันทึกงานที่ทำค้างไว้ใน `localStorage` ของเครื่อง (ครอบด้วย try/catch)
- ปุ่มส่งกดได้เมื่อ: จัดครบทุกใบ + ทุกกลุ่มที่มีการ์ดมีชื่อ
- หลังส่ง แสดงหน้าขอบคุณ พร้อมปุ่ม "ไปทำ Tree test ต่อ" และ "ทำใหม่ (ทับคำตอบเดิม)"

### 4.3 Tree test
- สุ่มเมนูให้ 1 แบบจาก A/B/C (ข้อ 5.2) และจำไว้ใน `treeVersion` แต่ละคนเห็นแค่เมนูเดียว
- โจทย์ 11 ข้อ (ข้อ 5.3) ข้อ 0 เป็นข้ออุ่นเครื่องเสมอ ส่วนข้อ 1–10 สลับลำดับแบบสุ่ม
- เมนูแสดงแบบ accordion ข้อความล้วน ไม่มีคำอธิบาย กดหมวดเพื่อกางหรือพับ กดชิ้นล่างสุดเพื่อเลือก แล้วกด "เจอแล้ว อยู่ที่ …" หรือ "หาไม่เจอ / ข้ามข้อนี้"
- เก็บต่อข้อ:
  - `chosen`, `path`, `success` (ชื่อที่เลือกอยู่ใน `a` ของโจทย์)
  - `direct` = ทุกหมวดที่เคยกางเป็นบรรพบุรุษของชิ้นที่เลือก
  - `firstTop` = หมวดระดับบนสุดของคลิกแรก
  - `timeMs`, `skipped`, `clicks` (เก็บไม่เกิน 40 คลิก)
- จบแล้วมีแบบสอบถาม: checkbox รายชื่อหมวดทั้งหมดในเมนูนั้น "ชื่อหมวดไหนเข้าใจยาก" และช่องความเห็น
- บันทึก `didCardSortFirst`

### 4.4 ผลลัพธ์ (รหัส 0000)
- หน้าใส่รหัส 4 ช่อง ใส่ผิดแล้วจอสั่น จำสถานะปลดล็อกไว้ใน `sessionStorage` และมีปุ่ม "ล็อก"
- subscribe `responses` ด้วย `onSnapshot` เพียงครั้งเดียว (unsubscribe เมื่อออกจากแท็บ)
- KPI: คนที่ตอบ / Card sort / Tree test / Tree test แยกเมนู A/B/C
- ปุ่ม **ส่งออก CSV** ผ่าน `downloads` capability มีคอลัมน์ `respondent, name, method, tree_version, task_or_group, value, success, direct, skipped, time_ms, path` และใส่ BOM ให้ Excel อ่านภาษาไทยได้
- แท็บย่อย: **ภาพรวม · IA จากผลลัพธ์ · Card sort · Tree test · ผู้ตอบ**
- ถ้ายังไม่มีคำตอบเลย ให้เปิดแท็บ "IA จากผลลัพธ์" พร้อมข้อมูลตัวอย่างให้เอง

**ภาพรวม**
- ตาราง Tree test เทียบ 3 เมนู: จำนวนคน, % หาเจอ (ไม่นับข้ออุ่นเครื่อง), % ไปตรงไม่ลังเล, เวลากลาง ไฮไลต์เมนูที่หาเจอสูงสุด
- ส่วน **"สิ่งที่ต้องทำกับ portal"** แปลผลอัตโนมัติ (ข้อ 6) เรียงแดง → ส้ม ก่อน
- กลุ่มเด่นจาก Card sort สูงสุด 8 กลุ่ม

**Card sort**
- กลุ่มที่แนะนำ: agglomerative clustering แบบ average linkage บน co-occurrence (สัดส่วนคนที่จัดการ์ด 2 ใบไว้กลุ่มเดียวกัน) มีแถบเลื่อนเกณฑ์ 0.2–0.9 ค่าเริ่มต้น 0.5
- ชื่อกลุ่ม = ชื่อที่คนตั้งให้กลุ่มที่มีการ์ดชุดนั้นอยู่อย่างน้อยครึ่งหนึ่ง นับชื่อแบบไม่สนตัวพิมพ์เล็ก/ใหญ่ แต่แสดงตัวพิมพ์ที่ใช้บ่อยสุด
- ตาราง "การ์ดแต่ละใบถูกจัดคู่กับอะไร" เรียงจากการ์ดที่คนจัดไม่ตรงกันที่สุด
- คลาวด์ชื่อกลุ่มที่ทีมตั้ง
- matrix co-occurrence แบบ heatmap อยู่ใน `<details>` เรียงตามกลุ่ม

**Tree test**
- ตารางรายโจทย์: % หาเจอ และ % ไปตรงไม่ลังเล แยกตามเมนู
- รายละเอียดแต่ละข้อ: "ทดสอบอะไร", สิ่งที่ต้องทำแยกตามเมนู, คำตอบที่คนเลือก (ไฮไลต์ข้อที่ถูก), คลิกแรกไปหมวดไหน, เวลากลาง, % ข้าม
- ชื่อหมวดที่คนบอกว่าเข้าใจยาก และความเห็น แยกตามเมนู
- **เลขข้อเริ่มที่ 0** ให้ตรงกับ diamond chart ใน Figma

**ผู้ตอบ**
- ตาราง: ชื่อ (`displayName` ก่อน ถ้าไม่มีใช้ชื่อบัญชีจาก `user.profiles()` แล้วแสดงชื่อบัญชีไว้ใต้ชื่อถ้าไม่ตรงกัน), สถานะ Card sort, เมนูของ Tree test, ลำดับที่ทำ, เวลาอัปเดตล่าสุด
- เก็บเฉพาะ id ในฐานข้อมูล ไม่เก็บชื่อจากบัญชี

  - Components: 42 ชิ้นเรียง A–Z

## 6. กฎแปลผล Tree test → สิ่งที่ต้องทำกับ portal

ใช้ตาม `GUIDE` ใน HTML เงื่อนไขประเมินแยกตามเมนู และใช้ % ของคนที่ทำข้อนั้นในเมนูนั้น
ระดับ: 🔴 ต้องแก้ · 🟠 ควรปรับ · 🔵 ปรับโครง/ลิงก์ · 🟢 ผ่าน

- **ทุกข้อ:** มีคนกดข้าม ≥30% → 🟠 เพิ่มทางเข้าอื่น เช่น ช่องค้นหาที่รู้จักคำเรียกอื่น
- **ไม่เข้ากฎข้อไหนเลย:** หาเจอ ≥75% → 🟢 ผ่าน ต่ำกว่านั้น → ดูคำตอบที่คนเลือกประกอบ
- **ภาพรวม:** เมนูที่ดีที่สุดหาเจอสูงกว่าเมนูที่แย่ที่สุด ≥15 จุด → ใช้โครงนั้นเป็นแกนของ portal ต่างกันน้อยกว่านั้น → เลือกโครงที่ดูแลง่าย
- ถ้าคนต่อเมนูยังน้อยกว่า **3 คน** ให้ติดป้าย "ข้อมูลยังน้อย ดูเป็นแนวโน้ม"
- กฎรายข้อ (เงื่อนไข → สิ่งที่ต้องทำ) อยู่ใน `GUIDE` และตรงกับ diamond chart ใน Figma ไฟล์ "Figma-Library-MS-Template" หน้า IA

เกณฑ์ % ทั้งหมดเป็นเกณฑ์ที่ทีมตั้งเอง ไม่ใช่มาตรฐานจาก NN/g ต้องเขียนบอกไว้บนหน้าเว็บ

## 7. IA จากผลลัพธ์ (dynamic)

มี 2 มุมมอง และแสดงได้ 2 แบบ:
- **แผนผัง** (ค่าเริ่มต้น): sitemap มีไอคอนบ้าน + "Design System Portal" อยู่บนสุด เส้นแนวนอนไปหาหัวหมวดสีฟ้า component ในแต่ละหมวดใช้สีเดียวกันและต่างสีกันระหว่างหมวด มีเส้นหักมุมพร้อมลูกศรเข้ากล่อง ระดับที่ 3 เป็นกล่องเส้นประเยื้องเข้าไป มีป้ายมุมกล่อง "ย้าย / ลิงก์ / ยังไม่ลงตัว" ข้อความใต้ชื่อสั้น ส่วนคำอธิบายเต็มอยู่ใน tooltip เลื่อนแนวนอนได้
- **รายการ:** แสดงคำอธิบายเต็ม

**จาก Card sort**
- หมวด = cluster ตามแถบเลื่อนเกณฑ์ ชื่อหมวด = ชื่อที่ทีมใช้บ่อยสุด ถ้าชื่อซ้ำกับหมวดอื่นให้ใช้ชื่อรอง แสดงชื่ออื่นที่ทีมใช้ด้วย
- การ์ดที่ค่าเฉลี่ยความเกาะกับหมวดอื่น ≥30% → ป้าย "ลิงก์" พร้อมข้อความ "↔ ชื่อหมวด %"
- การ์ดที่เกาะหมวดตัวเองต่ำกว่าเกณฑ์ → "ยังไม่ลงตัว"
- การ์ดที่ไม่เข้ากลุ่มไหน → รวมไว้ในหมวด "ยังไม่ลงตัว — ทีมจัดไม่ตรงกัน"

**จาก Tree test**
- เริ่มจากเมนูที่หาเจอสูงสุด แล้วปรับเฉพาะของในโจทย์ ต่อข้อ:
  - คนเลือกผิด แต่อยู่ **หมวดเดียวกับของที่ถูก** ≥30% → ป้าย "ยังไม่ลงตัว" + ข้อเสนอ "ปรับชื่อ" (เป็นปัญหาเรื่องชื่อ ไม่ใช่ตำแหน่ง)
  - หาเจอ <60% และคนไปหาหมวดอื่น ≥40% → ย้ายไปหมวดนั้น (ป้าย "ย้าย")
  - คนหาที่เดิม ≥30% และที่อื่น ≥30% → เพิ่มลิงก์ให้เจอได้สองที่ (ป้าย "ลิงก์")
- แสดงรายการสิ่งที่เปลี่ยนไว้เหนือแผนผัง

**ข้อมูลตัวอย่าง**
- ปุ่ม "ดูด้วยข้อมูลตัวอย่าง" จำลองด้วย seeded random: card sort 12 คน และ tree test เมนูละ 4 คน (ดู `sampleData()` ใน HTML)
- ต้องมีป้ายเตือนสีส้มว่าเป็นข้อมูลจำลอง
- ใช้ข้อมูลตัวอย่างเป็นค่าเริ่มต้นเฉพาะตอนที่ยังไม่มีข้อมูลจริง
- **ห้ามเขียนข้อมูลตัวอย่างลงฐานข้อมูล**

## 8. สิ่งที่ห้ามทำ

- ห้ามใช้ `alert/confirm/prompt` (ใช้ UI ในหน้าแทน) และห้ามใช้ `<a download>`
- ห้ามเก็บข้อมูลที่ต้องแชร์ใน `localStorage` (ใช้ได้แค่เก็บงานที่ทำค้างและชื่อที่พิมพ์ไว้)
- ห้ามเก็บชื่อหรือรูปจากบัญชีลงฐานข้อมูล เก็บเฉพาะ id กับ `displayName` ที่ผู้ตอบพิมพ์เอง
- ห้ามแก้ข้อความโจทย์ รายการการ์ด หรือเมนู ถ้าเจ้าของไม่ได้ขอ เพราะต้องตรงกับ diamond chart ใน Figma

## 9. เกณฑ์ว่าเสร็จ

- [ ] publish เป็น artifact ด้วย capabilities ตามข้อ 3
- [ ] ตรวจสิทธิ์ด้วย `as_level: "interact"` แล้ว ผู้ตอบมองไม่เห็นเอกสารของคนอื่น
- [ ] ทำ card sort และ tree test ครบ 1 รอบด้วยบัญชีเจ้าของ แล้วหน้าผลลัพธ์แสดงข้อมูลถูกต้อง
- [ ] **ลบข้อมูลทดสอบทั้งหมดก่อนส่งลิงก์ให้ทีม**
- [ ] แจ้งเจ้าของให้แชร์ลิงก์เป็น "Can interact" และย้ำว่ารหัส 0000 ไม่ได้ป้องกันข้อมูลจริง
